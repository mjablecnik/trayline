# Kiro Spec Format

A complete reference for creating, reading, and modifying Kiro specification files. Any agent or developer reading this document has everything needed to produce spec files that are structurally and semantically identical to those generated by Kiro.

---

## What Is a Kiro Spec?

A Kiro spec is a structured feature specification that lives in `.kiro/specs/<spec-name>/` and consists of exactly three Markdown files:

```
.kiro/specs/
└── <NNN>-<short-name>/
    ├── requirements.md   ← What to build (user-facing requirements)
    ├── design.md         ← How to build it (technical design)
    └── tasks.md          ← Step-by-step implementation checklist
```

The three files are written in a specific order and serve distinct purposes in the development workflow:

1. **requirements.md** — Defines what the feature must do, expressed as verifiable requirements grouped by concern. This is the contract between product and engineering.
2. **design.md** — Defines how the feature will be implemented: architecture, file structure, interfaces, data types, and algorithms. This is the blueprint for the implementer.
3. **tasks.md** — Breaks the implementation into an ordered, checkbox-driven task list. This is what the implementing agent (or developer) works through one task at a time.

---

## Spec Naming Convention

The spec folder name follows this pattern:

```
<NNN>-<short-name>
```

- `NNN` — zero-padded three-digit sequential number: `001`, `002`, ..., `042`, ..., `999`
- `<short-name>` — lowercase, hyphen-separated description of the feature area

Examples:
```
001-dashboard-api-projects
002-dashboard-api-git
003-dashboard-api-env
004-dashboard-frontend-setup
005-dashboard-frontend-projects
007-dashboard-frontend-git
008-dashboard-frontend-env
```

The number appears in the H1 heading of all three files. It identifies the spec and its order of implementation.

---

## Checkbox States

Requirements and tasks use standard Markdown task list syntax:

- `- [ ]` — not yet implemented / not yet completed
- `- [x]` — implemented / completed

**requirements.md** starts with all checkboxes in `[ ]` state. As implementation progresses, boxes are checked off.

**tasks.md** starts with all checkboxes in `[ ]` state. The implementing agent checks them off as each subtask is completed.

There is no in-between state. A checkbox is either done or not.

## File 1: requirements.md

### Purpose

Defines what must be built. Written in terms of observable, testable requirements. Does not describe implementation details — those go in design.md.

### Exact Structure

```markdown
# Requirements: <NNN> — <Feature Name>

## Overview

<2-4 sentences summarizing what this spec covers.>
<If there is a source of truth document (SPEC.md, PRD, etc.), reference it here.>
<If this spec depends on another spec, mention it by its full folder name.>

## Requirements

### REQ-1: <Requirement Group Name>
- [ ] <Concrete, verifiable requirement>
- [ ] <Another requirement in the same group>

### REQ-2: <Requirement Group Name>
- [ ] <...>

### REQ-3: <Requirement Group Name>
- [ ] <...>
```

### Rules for requirements.md

**Heading format:**
- The H1 is exactly: `# Requirements: <NNN> — <Feature Name>` using an em dash (`—`), not a regular hyphen
- `<NNN>` must match the number in the folder name
- `<Feature Name>` is the human-readable name of the feature (not the folder slug)

**Overview section:**
- 2–4 sentences maximum
- States what the spec covers, not how it will be implemented
- If a source-of-truth document exists (e.g., `dashboard/SPEC.md`), cite it with the relevant section references: `Source of truth: dashboard/SPEC.md (FR-1, FR-2, FR-3)`
- If this spec builds on another spec, state the dependency: `Dependencies: 001-dashboard-api-projects (git package, router)`
- Both "Source of truth" and "Dependencies" appear on separate lines after the summary sentences

**REQ sections:**
- Each `### REQ-N:` section groups related requirements under a single concern
- Typical number of REQ sections: 3–10 per spec (use judgment based on feature complexity)
- REQ section names describe the concern, not the action: `REQ-1: CORS Middleware`, `REQ-2: Project Discovery Configuration`, `REQ-5: GET /projects/{name}/tree/{ref}/{path...} — Directory Listing`
- For endpoint-focused specs, REQ sections often map one-to-one with API endpoints
- For UI-focused specs, REQ sections map to UI concerns: `REQ-1: Project List Page`, `REQ-2: Project Detail Shell`

**Checkbox items:**
- Each item is a single, independently verifiable requirement
- Be specific: mention exact field names, env var names, API routes, HTTP status codes, file paths
- Use present tense: "Return paginated commit log", "Display variables as a table/list"
- Do NOT describe implementation choices (what language, what library, what pattern to use)
- Each item should be answerable with yes/no: "Does it do X? Yes/No"

**What belongs in requirements vs design:**
- Requirements: `Return 404 if project not found` ✅
- Design: `Call resolveProjectPath() which lists the directory and checks name exists` ✅ (goes in design.md, not here)
- Requirements: `Values for keys containing KEY, SECRET, TOKEN, PASSWORD, or PRIVATE are masked by default` ✅
- Design: `Use SENSITIVE_PATTERNS array and isSensitive(key) helper function` ✅ (goes in design.md)

### Real Example (from spec 002)

```markdown
# Requirements: 002 — Dashboard API Git Module

## Overview

Add git history and uncommitted changes endpoints to the `remote/` server. Extends the `git/` package created in spec 001.

Source of truth: `dashboard/SPEC.md` (FR-4, FR-5)

Dependencies: 001-dashboard-api-projects (git package, router, project validation)

## Requirements

### REQ-1: GET /projects/{name}/commits — Commit History
- [ ] Return paginated commit log for a given ref (branch, tag, or hash)
- [ ] Query params: `ref` (default: current branch), `limit` (default: 50, max: 100), `offset` (default: 0)
- [ ] Each commit includes: hash, short_hash, message, author, date (ISO 8601)
- [ ] Response includes `total` count and `has_more` boolean
- [ ] Return 404 if project not found, 400 if ref is invalid

### REQ-2: GET /projects/{name}/commits/{hash} — Single Commit Detail
- [ ] Return full commit metadata: hash, short_hash, message, author, date
- [ ] Include stats: files_changed, insertions, deletions
- [ ] Include full unified diff as string
- [ ] Return 404 if commit hash not found in the project
```

## File 2: design.md

### Purpose

Defines how the feature will be built. This is the technical blueprint: file structure, component design, interfaces, data types, algorithms, and layout. The implementer reads design.md to understand every file they need to create or modify.

### Exact Structure

```markdown
# Design: <NNN> — <Feature Name>

## Overview

<1–3 sentences: technical summary of the approach. What is being built and how.>

## File Structure

<Directory tree of all files relevant to this spec.>

## <Section Name>

<Technical detail for one component, module, file, or concern.>

## <Section Name>

<...>
```

### Rules for design.md

**Heading format:**
- The H1 is exactly: `# Design: <NNN> — <Feature Name>` using an em dash (`—`)
- `<NNN>` and `<Feature Name>` must be identical to requirements.md

**Overview section:**
- 1–3 sentences maximum
- Describes the technical approach in concrete terms
- Example: `Extends the git/ package and adds handler endpoints for commit history, commit detail, and uncommitted changes.`
- Example: `SvelteKit static SPA scaffold with TypeScript, TailwindCSS, i18n, authentication, and deployment infrastructure.`

**File Structure section:**
- Always present when more than one file is involved
- Shows a directory tree using ASCII box-drawing characters
- Mark each file with a comment: `# NEW`, `# MODIFIED`, or omit comment for context files that are referenced but not changed
- Only include files directly relevant to this spec — don't list the entire project
- Use indentation to show hierarchy

File structure example:
```
remote/
├── api/
│   ├── cors.go                 # NEW — CORS middleware
│   ├── project_handler.go      # NEW — /projects endpoints
│   ├── project_types.go        # NEW — request/response types
│   └── router.go               # MODIFIED — register new routes
├── core/
│   └── config.go               # MODIFIED — add PROJECTS_DIR, DASHBOARD_ORIGIN
└── git/
    ├── git.go                  # NEW — git command runner with timeout
    ├── branch.go               # NEW — branch operations
    └── commit.go               # NEW — commit info
```

**Component/module sections:**
- One `## Section Name` per major file, component, or logical unit
- Section names are descriptive: `## Git Package`, `## Project Handler`, `## DiffViewer Component`, `## Route Registration`, `## Config Changes`, `## Response Types`
- Each section contains the full technical detail an implementer needs

**What to include in sections:**
- Type definitions and struct/interface declarations (in the actual language of the project)
- Function signatures with parameter names and return types
- Code examples for non-obvious patterns or algorithms
- ASCII layout diagrams for UI components
- Explanations of non-trivial logic (parsing, detection, validation algorithms)
- Constants, maps, or lookup tables that define behavior
- Sequence descriptions for multi-step flows

**Code blocks:**
- Always use fenced code blocks with a language tag: ` ```go `, ` ```typescript `, ` ```svelte `, ` ```css `, ` ```dockerfile `, ` ```env `
- Code in design.md is illustrative but should be accurate — the implementer uses it as a reference
- Include only the relevant parts of a struct/interface; don't include boilerplate
- Field names, JSON tags, and types must be precise — they define the API contract

**ASCII layout diagrams (for UI):**
Used when a component has a visual layout. Shows the structure using box-drawing characters and placeholder content:

```
┌─────────────────────────────────────────────────┐
│ ← Back to commits                               │
├─────────────────────────────────────────────────┤
│ fix: resolve login redirect                     │
│ Martin • 2 hours ago • 3 files (+12 −5)         │
├─────────────────────────────────────────────────┤
│ 📄 src/auth/login.go                    +8 −3   │
│ ┌───────────────────────────────────────────┐   │
│ │  15 │   func handleLogin(...) {           │   │
│ │  16 │-      http.Redirect(w, r, "/", 302) │   │
│ └───────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
```

**Tables:**
Used for structured reference data like status codes, color mappings, tab-to-route mappings:

```markdown
| Status | Color | Badge |
|--------|-------|-------|
| modified | yellow/amber | 🟡 |
| added/untracked | green | 🟢 |
| deleted | red | 🔴 |
```

**What NOT to include in design.md:**
- Task checklists (those go in tasks.md)
- Requirements re-statements (those are in requirements.md)
- Explanations of why requirements exist (that's product reasoning, not design)
- Boilerplate code that any developer would write without guidance
- Implementation notes about things that are obvious from the code itself

### Real Example (from spec 002, partial)

```markdown
# Design: 002 — Dashboard API Git Module

## Overview

Extends the `git/` package and adds handler endpoints for commit history, commit detail, and uncommitted changes.

## File Structure

```
remote/
├── api/
│   ├── git_handler.go          # NEW — /commits, /status endpoints
│   ├── git_types.go            # NEW — request/response types
│   └── router.go               # MODIFIED — register new routes
├── git/
│   ├── log.go                  # NEW — commit log with pagination
│   ├── show.go                 # NEW — single commit detail with diff
│   └── status.go               # NEW — working tree status with per-file diffs
└── ...
```

## Git Package Extensions

```go
// git/log.go
type LogResult struct {
    Commits []CommitEntry
    Total   int
}

func (r *Runner) Log(repoPath, ref string, limit, offset int) (*LogResult, error)
```

Implementation:
- Uses `git log --format=<custom> --skip=<offset> -n <limit> <ref>`
- Total count via separate `git rev-list --count <ref>`
```

## File 3: tasks.md

### Purpose

An ordered checklist of everything that needs to be implemented. Written to be worked through sequentially by an implementing agent or developer. Each task is a logical unit of work; each subtask within a task is a single concrete action.

### Exact Structure

```markdown
# Tasks: <NNN> — <Feature Name>

## Task 1: <Short task title>
- [ ] <Concrete subtask — one specific thing to create, modify, or implement>
- [ ] <Another subtask in the same task>
- [ ] <...>

## Task 2: <Short task title>
- [ ] <...>

## Task 3: <Short task title>
- [ ] <...>
```

### Rules for tasks.md

**Heading format:**
- The H1 is exactly: `# Tasks: <NNN> — <Feature Name>` using an em dash (`—`)
- `<NNN>` and `<Feature Name>` must be identical to requirements.md and design.md

**Task sections:**
- Each `## Task N:` is a logical unit of work that maps to one file, one component, one endpoint, or one closely related group of things
- Tasks are ordered by dependency: foundational things first, features that depend on them second, final wiring and polish last
- Typical pattern: data layer / utilities / types → core logic → API/handlers → UI → integration wiring
- Each task should be completable in approximately 30–90 minutes
- Aim for 7–15 tasks per spec (more for large features, fewer for small ones)
- Task titles are short and action-oriented: `Implement git log with pagination`, `Create deployment infrastructure`, `Implement save functionality`

**Subtask checkbox items:**
- Each item is one specific, concrete action with a clear done condition
- Reference exact file paths: `Create remote/api/git_handler.go`, `Update src/routes/[project]/env/+page.svelte`
- Reference exact function/method names from design.md: `Implement Log(repoPath, ref string, limit, offset int) (*LogResult, error)`
- Reference exact API routes, env var names, config keys from requirements.md and design.md
- Use imperative verbs: `Create`, `Add`, `Implement`, `Update`, `Parse`, `Handle`, `Render`, `Wire`
- A subtask is done when exactly one specific thing has been created or changed
- Do NOT have vague subtasks like `Make it work` or `Handle errors`

**Ordering within a task:**
- Subtasks within a task are also ordered by dependency
- For file creation tasks: first the file/struct skeleton, then method by method
- For component tasks: state/props definition → template → event handlers → styles

**Cross-referencing design.md:**
- Subtasks implicitly reference the design: if design.md says `Use git log --format=%H|%h|%s|%an|%aI`, the task says `Use git log --format=%H|%h|%s|%an|%aI` too
- The implementing agent reads both design.md and tasks.md; the tasks guide what to do, the design explains how

**What makes a good subtask (examples):**
- ✅ `Create src/lib/utils/diff.ts with parseDiff(raw: string): DiffFile[] function`
- ✅ `Use git log --format=%H|%h|%s|%an|%aI --skip=<offset> -n <limit> <ref>`
- ✅ `Return 404-type error for invalid hash`
- ✅ `Truncate individual file diffs > 500 KB (replace with placeholder message)`
- ❌ `Handle errors properly`
- ❌ `Add the necessary functionality`
- ❌ `Make sure it works`

**Checked vs unchecked:**
- All subtasks start as `- [ ]` when the spec is first created
- As implementation progresses, the implementing agent changes them to `- [x]`
- Mixed state (some checked, some unchecked) is normal during implementation — it shows progress
- A fully checked tasks.md means the spec is completely implemented

### Real Example (from spec 002)

```markdown
# Tasks: 002 — Dashboard API Git Module

## Task 1: Implement git log with pagination
- [x] Add `Log(repoPath, ref string, limit, offset int) (*LogResult, error)` to git package
- [x] Use `git log --format=%H|%h|%s|%an|%aI --skip=<offset> -n <limit> <ref>`
- [x] Parse output into `[]CommitEntry` structs
- [x] Get total count via `git rev-list --count <ref>`
- [x] Handle invalid ref gracefully (return specific error)

## Task 2: Implement git show (commit detail)
- [x] Add `Show(repoPath, hash string) (*CommitDetail, error)` to git package
- [x] Use `git show --stat --format=%H|%h|%s|%an|%aI <hash>` for metadata
- [x] Use `git diff-tree -p <hash>` for unified diff
- [x] Parse `--stat` summary line for files_changed, insertions, deletions
- [x] Extended timeout (10s) for large diffs
- [x] Return 404-type error for invalid hash
```

## How the Three Files Relate to Each Other

The three files form a directed chain:

```
requirements.md  →  design.md  →  tasks.md
   "What"           "How"          "Do it"
```

- Every REQ checkbox in requirements.md should be traceable to one or more sections in design.md
- Every section in design.md should result in one or more tasks in tasks.md
- Every task in tasks.md should implement something described in design.md that satisfies a requirement in requirements.md

If a task exists but has no backing in design.md, the design is incomplete.
If a design section exists but produces no tasks, either the tasks are missing or the design section is unnecessary.
If a requirement exists but nothing in design.md addresses it, the design is incomplete.

## Spec Scale and Complexity

Specs vary in size based on feature complexity. Here is the typical range observed across real specs:

| Feature Type | REQ sections | Design sections | Tasks |
|---|---|---|---|
| Single backend module (3-4 endpoints) | 4–8 | 5–8 | 8–12 |
| Full frontend scaffold | 7–9 | 6–10 | 8–12 |
| Single UI feature (one page/tab) | 4–7 | 4–7 | 6–10 |
| Small utility/extension | 2–4 | 3–5 | 4–7 |

Calibrate based on the actual scope. A spec for a single component should not have 20 tasks. A spec for a full module with 5 endpoints and types should not have only 3 tasks.

## Common Patterns by Project Type

### Backend Service (Go, Node, Python)

**requirements.md patterns:**
- REQ sections map to: individual endpoints, configuration, package/module foundations, security constraints
- Requirements state exact HTTP methods, paths, query params, request/response field names, error codes
- Authentication, validation, and error handling get their own REQ sections if they're non-trivial

**design.md patterns:**
- File Structure shows the Go/Node/Python source tree with new and modified files annotated
- One section per package or handler: `## Git Package`, `## Project Handler`, `## Route Registration`, `## Config Changes`
- Includes full Go struct/TypeScript interface definitions with field names and JSON tags
- Function signatures are precise: `func (r *Runner) Log(repoPath, ref string, limit, offset int) (*LogResult, error)`
- Algorithm explanations for parsing logic (git output parsing, binary detection, etc.)

**tasks.md patterns:**
- Task order: foundation types/packages → core logic → handlers → route registration → integration
- Each task = one file or one closely related set of functions
- Subtasks reference exact git commands, regex patterns, error types from design.md

### Frontend SPA (SvelteKit, React, Vue)

**requirements.md patterns:**
- REQ sections map to: individual pages, shared components, state management, API integration, responsive behavior
- Requirements state loading states, empty states, error states, user interactions
- Navigation, routing, and URL structure get explicit requirements

**design.md patterns:**
- Component Structure tree shows the component hierarchy and route file layout
- ASCII layout diagrams for each major UI component showing visual structure
- State interfaces in TypeScript for complex components
- Data flow descriptions (what gets fetched, when, how it flows to child components)
- Responsive CSS patterns (breakpoint-specific behaviors)

**tasks.md patterns:**
- Task order: utility functions → atomic components → composite components → page-level assembly → API integration → edge cases
- Each task = one component file or one closely related set of components
- Subtasks reference exact prop interfaces, store names, API calls, and CSS class patterns from design.md

## Writing a Spec from Scratch

### Step 1: Determine the spec number

Look at existing specs in `.kiro/specs/`. The next spec gets the next sequential number. If the last spec is `008-...`, the new one is `009-...`.

### Step 2: Write requirements.md first

1. Write the H1 heading with the spec number and feature name
2. Write the Overview: summarize the feature in 2-4 sentences, cite the source of truth document if one exists, mention dependencies on earlier specs
3. Identify the major concerns of this feature (each becomes a REQ section)
4. For each concern, list every concrete, verifiable requirement as a checkbox item
5. Review: can each item be independently verified as "done" or "not done"? If not, rewrite it

### Step 3: Write design.md second

1. Copy the H1 heading from requirements.md, changing "Requirements" to "Design"
2. Write the Overview: 1-3 sentences on the technical approach
3. Write the File Structure section showing all files to create or modify
4. For each major file or component, write a design section:
   - Paste in type definitions and function signatures
   - Add code examples for non-obvious patterns
   - Add ASCII diagrams for UI components
   - Explain algorithms and parsing logic in prose + code
5. Review: does every REQ from requirements.md have corresponding design coverage?

### Step 4: Write tasks.md last

1. Copy the H1 heading from requirements.md, changing "Requirements" to "Tasks"
2. Identify logical units of work from the design (one per major section/file)
3. Order tasks by dependency (what must exist before what)
4. For each task, list concrete subtasks with exact file paths, function names, and references from design.md
5. Review: does every section in design.md produce at least one task? Does the task list, if completed in order, fully satisfy all requirements?

## Modifying an Existing Spec

### Adding requirements mid-implementation

Add new `- [ ]` items to the appropriate REQ section in requirements.md. Add corresponding design coverage in design.md. Add new tasks or subtasks in tasks.md.

Do NOT renumber existing REQ sections when adding new ones. Append: if the last section is `REQ-5`, add `REQ-6`.

### Marking progress

As subtasks are completed, change `- [ ]` to `- [x]` in tasks.md.
When all subtasks in a task are done, the `## Task N:` heading itself is considered complete (no separate heading-level checkbox).

Optionally, also check off the corresponding requirements in requirements.md as they are satisfied. This is done by the implementing agent as it progresses.

### Splitting or merging specs

If a spec grows too large (>20 tasks), split it into two specs with sequential numbers. The new spec gets the next available number and lists the original spec as a dependency.

If two small specs turn out to be trivially related, they can be merged. Renumber if needed to maintain sequential ordering.

## Checklist for Spec Quality

Use this checklist before treating a spec as ready for implementation:

**requirements.md:**
- [ ] H1 heading uses em dash (`—`) not hyphen (`-`)
- [ ] Spec number in H1 matches folder name
- [ ] Overview cites source of truth and dependencies
- [ ] Each REQ section covers a single concern
- [ ] Every checkbox item is concretely verifiable
- [ ] No implementation details in requirements (no function names, no specific libraries)

**design.md:**
- [ ] H1 heading matches requirements.md (same number and name)
- [ ] File Structure shows all new and modified files annotated
- [ ] Every significant file has a design section
- [ ] Type definitions use the actual project language (Go structs, TS interfaces)
- [ ] UI components have ASCII layout diagrams
- [ ] No task checklists in design.md
- [ ] Every REQ is addressed somewhere in the design

**tasks.md:**
- [ ] H1 heading matches requirements.md (same number and name)
- [ ] Tasks are ordered by dependency (foundation before features)
- [ ] Every task has a clear, short title
- [ ] Every subtask references exact file paths, function names, or values
- [ ] All checkboxes start as `- [ ]` (or partially checked during implementation)
- [ ] Every design section results in at least one task
- [ ] Completing all tasks would fully satisfy all requirements
