## RingBuffer.Wrapped() was implemented but never wired through any API response or WebSocket message
- Project: trayline (remote + dashboard, 010-dashboard-workflow-runner spec, task 11.1 — WorkflowLogViewer.svelte)
- Problem: Requirement 13.6 requires the log viewer to show a "truncated" notice when a workflow's 1MB ring buffer wraps. `store.RingBuffer.Wrapped()` (task 1.2/1.3) was fully implemented and property-tested, but `grep -rn "\.Wrapped()"` across `remote/` showed it was called only from `ringbuffer_test.go` — never from `api/workflow_types.go`'s `workflowToResponse` (the REST detail/list JSON) or `api/workflow_handler.go`'s `workflowLogMessage` (the WebSocket protocol). Neither the design doc's `Workflow` TypeScript interface nor its WS message shapes (`{type:"finished",...}`) included a truncation field either — so there was no way for the frontend to ever learn a workflow's log had been truncated, even though the backend tracked it correctly internally. This is the same class of gap as the earlier-documented "no backend endpoint exists to fetch raw file bytes" entry: a downstream frontend task cannot faithfully satisfy its requirement because an upstream task's spec/design silently omitted the plumbing.
- Solution: Added `Truncated bool \`json:"truncated,omitempty"\`` to `WorkflowResponse` (set from `w.LogBuffer.Wrapped()` only when `includeLog` is true, mirroring how `Log` itself is conditional) and to `workflowLogMessage` (set in `sendFinished` from `wf.LogBuffer.Wrapped()`, covering both the live-stream-to-completion path and the terminal-replay-then-finish path, since both call `sendFinished`). Added the matching `truncated?: boolean` field to the frontend `Workflow` interface in `api.ts`. This was a 2-line backend change surfacing an already-computed, already-tested value — not new business logic — so it was safe to fold into the frontend task rather than deferring it. When a future task depends on a value a backend struct field computes internally (`Wrapped()`, or any other unexported-from-JSON getter), grep for `.MethodName()` call sites before assuming a `_test.go`-only hit means the feature is actually reachable from the API.

## Seeding $state()'s initializer from a prop triggers Svelte 5's state_referenced_locally warning even when the prop is intentionally read only once
- Project: trayline (dashboard, 010-dashboard-workflow-runner spec, task 10.1 — WorkflowForm.svelte)
- Problem: `WorkflowForm.svelte` is only ever mounted fresh per open (parent wraps it in `{#if showForm}`), so its `editingWorkflow` prop is a one-shot "initial value" by construction — it never changes while the component is alive. Writing the natural-looking `const isEdit = editingWorkflow !== null;` and `let selectedPipeline = $state(editingWorkflow?.pipeline ?? DEFAULT_PIPELINE);` (mirroring the existing `EnvEditor.svelte`-style "seed local state from a prop" pattern) type-checks with 0 errors under `svelte-check`, but produces 2 `state_referenced_locally` warnings ("This reference only captures the initial value... Did you mean to reference it inside a closure/derived instead?") — Svelte 5 can't statically distinguish "intentionally snapshot once" from "forgot to make this reactive", so it warns on any bare read of a prop/`$state` value used only to seed another binding's initializer.
- Solution: Wrap the intentional one-shot reads in `untrack(() => ...)` (imported from `'svelte'`): `const isEdit = untrack(() => editingWorkflow !== null);` and `let selectedPipeline = $state(untrack(() => editingWorkflow?.pipeline ?? DEFAULT_PIPELINE));`. This documents the "read once, not reactive" intent explicitly and silences the warning without changing behavior (0 warnings after). Use this whenever a component is guaranteed to be freshly remounted per logical "session" (modal/dialog forms behind an `{#if}`, not always-mounted components) and needs to seed local state from a prop that should NOT resync if the prop later changes.

## store.WorkflowStore.Get()/ListByProject() return live *Workflow pointers whose fields race with concurrent Update() calls
- Project: trayline (remote, 010-dashboard-workflow-runner spec, task 4 — WorkflowQueueManager)
- Problem: `WorkflowStore.Get(id)`/`ListByProject(project)` (and the equivalent pattern in `store/task.go`/`store/session.go`) return the store's actual `*Workflow` pointer, not a copy. `WorkflowStore.mu` only guards the map/slice structure — it is NOT held while a caller reads fields off a previously-obtained pointer. Once `WorkflowQueueManager.runWorkflow`/`finishWorkflow` started mutating a workflow's `Status`/`ExitCode`/`Error` fields via `store.Update(id, fn)` from its processor goroutine, a test (and, in the future, any HTTP handler like `HandleDetail`/`HandleList` in task 5.4) that does `w := store.Get(id); use(w.Status)` concurrently is a genuine data race — caught by `go test -race` (`CC=cc CGO_ENABLED=1 go test -race ./api/...`, per an existing memory entry on this repo's race-detector setup), not just a test artifact. It reproduced deterministically in `TestWorkflowQueueManager_SequentialExecutionPerProject`/`_CrossProjectParallelism` polling a workflow's status while the queue manager was simultaneously finishing it.
- Solution: Never read a field off a `Get()`/`ListByProject()` pointer while the workflow could still be mutated concurrently. Instead route the read back through `store.Update(id, func(w *Workflow) { snapshot = w.Status })` (or copy the whole struct: `func(w *Workflow) { snapshot = *w }`) so the read happens under the store's lock, same as the write. It's only safe to read a raw `Get()` pointer's fields directly once the workflow is confirmed terminal (`store.IsWorkflowTerminal`) via a lock-protected read first, since the queue manager never mutates a workflow again after that. When task 5.4 (`HandleDetail`/`HandleList`) is implemented, apply the same pattern (or accept the race if this codebase's task/session handlers already have the identical pre-existing pattern un-flagged — check whether their handlers are ever exercised under `-race` with a concurrently-running container before assuming it's fine there too).

## TestWorkflowStore_SequentialExecutionPerProject double-counts running workflows when rapid draws duplicate project names
- Project: trayline (remote/store, 010-dashboard-workflow-runner spec, task 1.5, discovered while doing task 3)
- Problem: `rapid.SliceOfN(rapid.StringMatching(...), 1, 5).Draw(t, "projects")` for the `projects` slice in `TestWorkflowStore_SequentialExecutionPerProject` is not deduplicated, so it can draw e.g. `["a", "a"]`. The test's final tally loop was `for _, project := range projects { for _, w := range s.ListByProject(project) { if w.Status == WorkflowRunning { runningCount[project]++ } } }` — when the same project name appears twice in the slice, its running-workflow count gets added twice, so a store with exactly 1 running workflow for project "a" reports `runningCount["a"] == 2` and the test fails with "expected at most 1" even though `WorkflowStore` itself is correct. This is a real, deterministically reproducible failure (not a flake) for any rapid seed that draws a duplicate project name — it was left unnoticed because the task-2 checkpoint's test run happened not to hit that seed.
- Solution: Dedupe `projects` into a `map[string]bool` before the tally loop and range over that map's keys instead of the raw slice. Confirmed the bug pre-dates task 3 (reproduces identically with `git stash` applied, i.e. on the unmodified task-1 commit) via `go test ./store/... -run TestWorkflowStore_SequentialExecutionPerProject -rapid.seed=5934142376623854387`. General lesson: any rapid/gopter property test that draws a slice of "entity names" to iterate over twice (once to build state, once to tally results) needs deduplication before the tally pass, or duplicate-valued slices will double-count.

## git show <ref>:<path> succeeds for directory paths and returns a tree listing, not an error
- Project: trayline (remote, 001-dashboard-api-projects spec)
- Problem: `git show <ref>:<path>` does not fail when `<path>` resolves to a directory (tree) rather than a file (blob) — it exits 0 and prints a plain-text tree listing to stdout instead. A naive `git.Blob(repoPath, ref, path)` built on `git show` alone would silently return that listing as if it were file content for any directory path, instead of erroring, which would misbehave badly in the future blob HTTP endpoint (task 11): a client requesting `/blob/<ref>/src` (a directory) would get 200 with fake "file content" instead of a 404.
- Solution: Before calling `git show`, resolve the object type with `git cat-file -t <ref>:<path>` and require it to be exactly `"blob"`; treat anything else (`"tree"`, missing object, bad ref) as `ErrNotFound`. See `remote/git/tree.go`'s `Blob()`.

- Problem: When a flat `package main` (orchestrator/) is split into `core`/`llm`/`engine`/`cmd`, several small unexported helpers that were implicitly shared because everything compiled into one package become unreachable across the new boundaries: (1) `mockEvaluator` (a ConditionEvaluator test double defined in the old `executor_test.go`) was also used by `llm_logger_test.go` — after the split, `llm/logger_test.go` needed its own copy since it can't import engine's unexported test type. Also watch for a compiler-feedback loop with `go build ./package` iterated per package (leaf packages `core`/`llm` first, then `engine`, then `cmd`) — it surfaces every one of these strandings as an `undefined: X` error, which is far faster than trying to plan all qualifications up front.

## DELETE-cancelling a running workflow races the queue processor's own exit-code-based status decision unless the processor defers to a "cancel requested" flag
- Project: trayline (remote/api, 010-dashboard-workflow-runner spec, task 5.4 — workflow CRUD handler)
- Problem: Requirement 6.6 says cancelling a *running* workflow must end with status "cancelled", but `WorkflowQueueManager.runWorkflow` (task 4, already implemented before this task) determines the final status purely from the container's exit code/timeout after its `<-copyDone` unblocks: a SIGTERM/SIGKILL-induced exit is a non-zero exit code like any crash, so without intervention `runWorkflow` reports "failed" (with a bogus stderr-derived error message) for any container HandleCancel kills, not "cancelled". (2) Making `HandleCancel` block synchronously for up to the 10s SIGTERM grace period (naively reading Req 6.6's "send SIGTERM... wait up to 10 seconds... send SIGKILL... set status" as a sequential recipe the HTTP handler itself must perform) — every other handler in this codebase returns immediately; blocking the request goroutine for up to 10s is out of character and unnecessary since the frontend just polls/refreshes the list (Req 12.6).
